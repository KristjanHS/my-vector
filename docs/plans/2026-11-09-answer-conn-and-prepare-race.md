## [USER DECISION] P2 — how a Cancel stops hitting the previous stream

vic-anim sends nothing on an accepted Prepare (only failures); the engine forwards only Completed / BufferOverflow / Prepare-Post-AddAudio-Failed; no message carries a stream id; only the gateway sends ExternalAudioCancel.

- **a — stream ids end to end.** Buys: exact attribution of every message both ways, retires the `completeSent`/`verdict` heuristics, survives any later multi-stream change. Costs: biggest change — public proto, 5 CLAD messages, engine, vic-anim, gateway; three binaries ship together; largest patch to carry across WireOS rebases.
- **b — gateway waits a bounded time before the close-Cancel.** Buys: vic-cloud only, ~15 lines. Costs: with no positive Prepare ack, every legit unfinished close pays the full wait before the next stream can open; only narrows the race to "PrepareFailed slower than T" (likeliest when vic-anim is loaded); the refused stream's chunks/Complete can still reach the playing stream.
- **c — vic-anim ignores everything after a refused Prepare.** Buys: one vic-anim file, ~15 lines; also stops the refused stream's chunks/Complete touching the playing stream; clients still see PrepareFailed as today. Costs: correct only while the gateway admits one stream at a time — silently wrong if that rule is ever lifted; needs a vic-anim build.
- **d — gateway holds the slot until playback ends.** Buys: vic-cloud only; removes the precondition (no Prepare reaches vic-anim while it plays), covers chunks too. Costs: the next stream gets ResourceExhausted for up to the buffered audio length instead of PrepareFailed, so chipper's single 200 ms retry must change (P2.d2); the engine subscription must outlive the gRPC handler.
